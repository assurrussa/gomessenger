# GoMessenger v0.3.0

These notes describe GoMessenger v0.3.0.

## Changes

The release adds explicit producer, relay and consumer batching across the durable messaging pipeline. Typed batch
send/publish calls stage all messages atomically through the Outbox batch producer. Relay batches use bounded
asynchronous NATS publication or one Kafka transaction. Existing single-message constructors retain their behavior;
reservation/prefetch size alone does not enable batch execution.

NATS and Kafka batch consumers invoke a batch handler once per Inbox/business transaction. The handler classifies every
input before writing SQL and writes only for successful items. Results cover each logical message exactly once;
invalid results fail the consumer closed. `DeferAfter` postpones an item without consuming its retry budget.

Terminal Inbox generations now survive permanent/exhausted handoff, restarts and attempt-limit increases. Retention is
opt-in and requires confirmed handoff; it never installs a default TTL. NATS captures that cannot fit replayable DLQ v1
become bounded quarantine v2. Quarantine preserves diagnostic identity and sizes and is never replayable. Local queued
commands and events also recheck expiry before entering middleware or a handler.

Go remains on 1.27. GoBus is pinned to v1.2.1; Outbox root and the host's corresponding database backend must both use
v0.15.0. The root facade still depends only on the standard library and GoBus. See the [changelog](../../CHANGELOG.md)
and [public contracts](../contracts.md) for the complete behavior.

## Upgrade from v0.2.2

Keep all GoMessenger modules on the same released version. Once v0.3.0 has passed published verification, update the
root, used adapters, optional observability module and CLI together. Keep Outbox root and its database backend at
v0.15.0. Install and validate the new CLI before consumers can write quarantine v2.

1. Apply the additive PostgreSQL/SQLite Inbox migration through the existing `Migrate` entry point, with the same
   schema/prefix options used by the store. Reapplication is idempotent.
2. Drain and stop every old consumer that can still delete terminal attempt state.
3. Start the new consumers, confirm readiness and inspect terminal handoff errors.
4. Enable terminal pruning separately only after the host selects a safe cutoff that accounts for broker retention
   and delayed or in-flight deliveries.

Messages deferred by older code acquire a zero-attempt marker only upon redelivery under the new code; let them
redeliver before enabling terminal pruning, as upgrading the binary does not retroactively backfill missing generation
markers.

Mixed old/new consumers are unsafe for terminal protection because old binaries can erase attempt counters. Historical
permanent outcomes migrate without inferred ACK confirmation; previously deleted attempt history cannot be recovered.
Rolling back to an old consumer restores its old deletion behavior. See the
[delivery upgrade contract](../decisions/0006-delivery-guarantees.md#deployment-and-compatibility).

## Release evidence

All seven GoMessenger modules are published at exact version `v0.3.0` and verified through `make test-consumer-release VERSION=v0.3.0`
without development replacements.

The release candidate verified the fixed-rate capacity series on clean commit `abc9f0a` (tree identical to release head):
**PASS, 6 of 6 runs met sustainable throughput and latency boundaries**.

| Run | Relay / consumer, msg/s | p95 latency | Lag outbox / consumer | Drain | Reconciliation |
|---|---:|---:|---:|---:|---:|
| small-r1 | 1499.2 / 1499.2 | 127.5 ms | 100 / 0 | 0.90 s | 180,100 / 180,100 |
| mixed-r1 | 1499.2 / 1499.2 | 179.0 ms | 100 / 0 | 0.78 s | 180,000 / 180,000 |
| small-r2 | 1499.2 / 1499.2 | 127.3 ms | 100 / 0 | 0.68 s | 180,100 / 180,100 |
| mixed-r2 | 1499.2 / 1498.3 | 189.4 ms | 100 / 100 | 0.86 s | 180,000 / 180,000 |
| small-r3 | 1499.2 / 1499.2 | 125.1 ms | 100 / 0 | 0.77 s | 180,100 / 180,100 |
| mixed-r3 | 1499.2 / 1499.2 | 184.5 ms | 100 / 0 | 1.04 s | 180,100 / 180,100 |

Across all runs, `sustainable=true`, `integrityPassed=true`, drain completed cleanly. All accepted messages were published
and processed with zero invalid measurements and zero missing correlations.

Library source checks, published-module verification and capacity measurements remain separate from the
[real-service pilot](../decisions/0002-real-project-pilot.md). At-least-once delivery does not promise exactly-once
external effects or global ordering.
