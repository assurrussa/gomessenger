# GoMessenger v0.4.0 release candidate

Status: staged publication. Root `v0.4.0` is published at
`7adc402895a9f8e4680103d3db718f72d5f52b96` and resolves through the public Go
proxy. The root-dependent module layer is prepared and source-checked; its
three tags, the transport and final layers, and the clean published-consumer
gate remain outstanding. The complete v0.4.0 module set is not yet released.

## Contents and compatibility

This candidate includes the seven merged changes since v0.3.1:

- [PR #37](https://github.com/assurrussa/gomessenger/pull/37): canonical local
  metadata and child lineage survive middleware context replacement;
  `nats.HandlerConfig.MaxAckPending` configures the shared durable ACK window.
- [PR #38](https://github.com/assurrussa/gomessenger/pull/38): the PostgreSQL
  atomic Inbox/business/Outbox example.
- [PR #39](https://github.com/assurrussa/gomessenger/pull/39): manual-only CI and
  benchmark workflows.
- [PR #40](https://github.com/assurrussa/gomessenger/pull/40): message/duplicate
  counters, batch-size observations and selected batch-outcome metrics.
- [PR #41](https://github.com/assurrussa/gomessenger/pull/41) and
  [PR #42](https://github.com/assurrussa/gomessenger/pull/42): LocalAsync payload
  ownership, SQL batch retry, application-owned aggregate ordering and explicit
  durable-demo dependency modes.
- [PR #43](https://github.com/assurrussa/gomessenger/pull/43): offline, pinned
  JSON Schema baseline checks in `gomessengerctl`.

It also composes the merged
[PR #44 Kafka comparison](https://github.com/assurrussa/gomessenger/pull/44)
with the reviewed NATS process and synthetic-pilot fixtures. PR #44 merged on
2026-10-10 at 16:13:31 UTC as
`019a1b6109f112b54205c39400cadba33d304d57`; the merge tree exactly matches its
reviewed final head. This source packet is based on that merged tree.

Go remains at 1.27 and GoBus at v1.2.1. The NATS configuration field is additive,
but existing unkeyed `HandlerConfig` literals must become keyed literals.
Zero retains the previous ACK-window defaults; negative values are rejected.
The shared window is separate from per-replica worker/prefetch limits and does
not promise replica fairness or silently change an existing durable.

Batch metrics record selected decisions, not confirmed broker finalization.
The ordering example does not promise Kafka ordering across retry topics.
Schema checking enforces pinned baseline identity and immutable document
versions with sample validation; it is not general schema compatibility,
Go-codec conformance or runtime validation.

## Dependency layers and remaining gates

The selected target is Outbox root, PostgreSQL backend and SQLite backend
v0.17.0 together. Those upstream tags are published. The prepared modules
layer pins Inbox, the Outbox adapter and observability to published root
v0.4.0; the Outbox adapter selects Outbox v0.17.0. The checkout-only E2E
fixture requires root v0.4.0 and published Outbox root/SQLite v0.17.0,
retaining its GoMessenger checkout replacements and later adapter requirements.
Transport, CLI and consumer module requirements remain at v0.3.1 until their
layers. The atomic PostgreSQL example retains Outbox root v0.16.0 and backend
v0.16.1-0.20261009035614-46f29a8e18e1 until final preparation.

The root module has no Outbox dependency. The root preparation script verifies
that the selected upstream prerequisites resolve, checks that root has no
replacement and tidies only root. The Makefile target then formats Go files
across the checkout, excluding tmp; every resulting change must be inspected.
Root release-readiness alone checks replacement state, not prerequisite
resolution or runtime correctness. Root preparation must not advance nested
requirements before root v0.4.0 is published.

Follow the [release process](../release.md) without changing workflow triggers:

1. Prepare, check and review the exact root-layer commit; publish `v0.4.0`
   only after the release gates are satisfied.
2. Once root resolves, prepare/review the Inbox, Outbox-adapter and
   observability layer, adopting Outbox v0.17.0 where selected by the canonical
   script; publish their three path-qualified v0.4.0 tags.
3. Once Inbox resolves, prepare/review NATS and Kafka; publish their two tags.
4. Once all six prerequisites resolve, finalize CLI/consumer/example/E2E
   requirements, verify final release readiness and publish
   `tools/gomessengerctl/v0.4.0`.
5. Verify all seven immutable origins/checksums, run
   `make test-consumer-release VERSION=v0.4.0` without replacements, and
   record the actual public consumer and CLI-install results before updating
   the README's published installation surface.
